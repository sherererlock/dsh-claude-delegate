自测

Q1. 一个插件被 dsh 加载，最少需要哪几个文件？
参考答案
入口模块（至少导出 apply；通常还有 name / inject）、package.json（含 dsh.bundle.patch）、cordis.patch.yml。TypeScript 与 .d.ts 是发布要求，不是加载前提。
Q2. --dump-config 能看到条目，就说明插件加载成功了吗？
参考答案
不。它只把 bundle、profile、overlay 三层 YAML 组合后打印，不 import 模块。要证明加载，必须 boot 一次。
Q3. patch 里的 config 是深合并还是整体替换？
参考答案
整体替换。只写一个字段会把同一条目的其余配置项丢掉；没写的字段回到 schema 默认值，不会保留 patch 之前的值。
Q4. 新建的 profile 启动后为什么可能静默挂起？
参考答案
它默认只有 @deepseek-ai/dsh-base，没有 app。把 @deepseek-ai/dsh-headless 或 web 加进 dsh.profile.bundles，才会出现可交互入口或明确的 a task is required 报错。

Q1. as const 解决了什么问题？

关键代码

一个插件模块用 apply 声明行为；name 用于诊断信息，inject 声明服务依赖，两者都是可选导出。Cordis 挂载它时创建一个 fiber；inject 里的服务全部就绪，才调用 apply(ctx, config)。缺一个，fiber 停在 PENDING，apply 不会执行。

最小骨架（对照 src/index.ts）
1import { Service, type Context } from '@deepseek-ai/cordis'2import z from '@deepseek-ai/schemastery'3 4export const name = 'claude-demo'5export const inject = ['tools']6 7export interface Config {8  greeting: string9}10 11export const Config: z<Config> = z.object({12  greeting: z.string().default('hello'),13})14 15class DemoService extends Service {16  constructor(ctx: Context) {17    super(ctx, 'claudeCodeDemo')18  }19}20 21export function apply(ctx: Context, config: Config) {22  new DemoService(ctx)23  console.log(config.greeting)24 25  const jobs = ctx.get('jobs')26  if (jobs === undefined) return27  // 这个 profile 没有 jobs 服务：apply 照常跑完，不阻塞 fiber28}

inject 声明的是硬依赖。Cordis 4.x 没有 optional-inject：{ required, optional } 这种对象写法会被当成两个字面量服务名，fiber 直接卡死。要可选，就在用到时 ctx.get('name')；服务不存在返回 undefined，不会阻止插件启动。

Service 子类在构造函数里 super(ctx, '名称') 就完成注册，卸载时随 fiber 自动移除。Config 用 schemastery 定义字段和默认值，apply 拿到的是解析后的对象。patch 里的 config 整体替换整份配置，不是逐字段深合并。

自测

Q1. defineTool 的四段分别是什么？哪一段写业务逻辑？
参考答案
身份（name + description）、parameters、output（schema + render）、execute。只有 execute 写业务逻辑；output.render 只是把校验后的规范值格式化成模型可见内容。timeoutMs 是附加的调度元数据。
Q2. 参数校验发生在 execute 之前还是之后？校验失败时 execute 会跑吗？
参考答案
之前。注册表按 parameters 校验模型传来的 arguments，失败就走工具错误路径，execute 不会执行。所以 execute 里不用再写一遍类型和必填检查。
Q3. execute 返回的对象和 output.render 返回的 content blocks，哪个是模型看到的？
参考答案
render 的返回值。execute 的返回值先按 output.schema 校验，再交给 render；模型上下文里只有 render 产出的 content blocks。execute 的返回值是给程序化调用方和 render 用的规范值。
Q4. presentCall 和 output.render 有什么区别？
参考答案
output.render 决定模型可见内容；presentCall 决定 UI 的 pending 卡片（标题、图标、原始参数）。两者互不影响，UI 展示失败也不该让工具结果失败。
Q5. timeoutMs 写 0 会发生什么？
参考答案
注册表要求 timeoutMs 是正的有限值，0 可能让工具注册失败。配置里要给正数；长任务按需放大，不要用 0 表示「不超时」。

自测

Q1. 面板的三路 job 源分别是什么？为什么要合并？
参考答案
0.2 的 ctx.jobs 名册（jobs.state）、0.1.x 的 useSessions 镜像（jobsBySession）、插件自己的 listJobs 轮询结果（tracked）。合并是为了同时兼容 0.1.x 和 0.2，并且自己的 tracker 不会漏掉刚启动的作业。
Q2. 1 秒轮询什么时候开？什么时候关？
参考答案
只在面板挂载、选中会话还有 running 作业时开；作业进入终态后触发一次最终读取，然后不再开定时器。effect 的 cleanup 会 abort 读取并 clearInterval。ClaudeCodeView.tsx:381-441。
Q3. 当前 installStyles() 的问题是什么？怎么修？
参考答案
它只注入 <style>，没有 remove；卸载或 HMR 后标签留在 <head>，HMR 时旧内容也不会更新。加 removeStyles()，用 ctx.effect(() => { installStyles(); return removeStyles }) 注册清理。
Q4. 为什么 slots.register 要包在 slots.inject 里？
参考答案
bundle 可能早于 ui-conversation 声明 conversation.view 加载，裸 register 会抛错。inject 等 owner 声明后运行回调，owner 折叠时注册随 effect 移除，重新挂载时再运行。
Q5. 面板状态为什么放在模块级缓存，而不是组件 state？
参考答案
harness 会卸载非活动视图，组件 state 在切 tab 时丢失；模块级 panelOf(sessionId) 保留选中任务、已读偏移和输出缓存，切回来能接着读。这是本项目的视图生命周期约束，不是通用模式。

官方推荐 vs 本项目做法

官方推荐：Cordis 未管理的资源（定时器、连接、watcher、DOM 副作用）包在 ctx.effect() 里，并返回 disposer；卸载和 HMR 时都会执行。出处：cordis-tutorial/02-lifecycle-and-effects。

本项目做法：client/index.ts:26 直接调 installStyles()；styles.ts:882-891 只检查 #STYLE_ID 是否已存在，然后 append，没有 remove 函数。

差异：卸载后 <style> 留在 <head>；HMR 时靠 id 去重，旧标签挡住新内容，样式更新不会生效。

原因：一次性注入实现最简单；开发时全页刷新居多，HMR 的样式残留不容易暴露。

你该怎么做：照练习 5.2 加 removeStyles()，用 ctx.effect 返回 cleanup。不要复制「只 install 不 cleanup」的写法；在卸载时释放自己申请的资源。

官方推荐：客户端的作业数据走生成的 Remote 流（job.list / job.follow）和 client model：model 维护稳定快照，UI 订阅，不在组件里复制 transport state，也不轮询。出处：subsystems/jobs、subsystems/web-client。

本项目做法：ClaudeCodeView 合并三路源：jobs.state、useSessions.jobsBySession、自己的 listJobs 轮询（2 秒）；选中任务 live 时再 1 秒轮询 readEvents / readOutput（:231-242, :279, :381-441）。

差异：官方一套推送源加一个 client model；本项目三套源去重，加两档轮询，transport state 直接进组件。兼容路径多了，代码也就多了。

原因：要同时兼容 0.1.x（镜像）和 0.2（jobs 服务）；自己的 tracker 是唯一不会漏掉刚启动作业的源；官方 job 流没有结构化事件，live 文本也没有对应的 Client→Host 推送，只能轮询。harness 卸载视图又逼着把状态搬到模块级缓存。

你该怎么做：只面向一个 DSH 版本时，用生成的 jobs client model 和 job.follow，不要抄三路合并。必须轮询时，照这里的生命周期：只在挂载且任务运行时开表，cleanup 清掉，状态不要只放组件 state，卸载时会丢。先确认官方有没有推送，再决定轮询。

三个实测坑

  1. 全局 TypeScript 6 与本项目 ^5.4.5 不兼容。本机全局 typescript 是 6.0.3；TS 6 把 baseUrl 的弃用从警告升级成 error（TS5101），tsc 直接退出。构建和类型检查都用项目自己的 node_modules/typescript：npm run build、npm run typecheck 会自动用本地版本，不要直接调用全局 tsc。
  2. tsc 类型报错仍会产出 JS。noEmitOnError 默认是 false，所以 lib/index.js 存在不代表编译成功，assert-artifacts 通过也不代表类型正确——它只查文件是否存在、大小是否为 0。判断标准是 tsc 的退出码和错误输出；发布前单独跑一次 npm run typecheck。
  3. peer 范围是强制检查，不是文档约定。dsh plugin add 会读 peerDependencies；存在 engines.dsh 时以它为准。不兼容会直接拒绝安装，并打印 allow-version ... --accept-risk 豁免命令，错误信息写明可能崩溃或丢数据。实测把 peer 写成 >=99.0.0，安装被拒。devDependencies 不参与兼容判断；peerDependenciesMeta.optional 的 peer（本项目的 react 与客户端 primitives）缺失时不阻塞。

自测

Q1. lib/index.js 已经生成，能说明 tsc 编译成功吗？
参考答案
不能。noEmitOnError 默认 false，类型错误仍会产出 JS。看退出码和错误输出；发布前跑 npm run typecheck。assert-artifacts 只查文件存在和大小，不查类型。
Q2. 为什么宿主和客户端要两套 tsconfig？
参考答案
运行环境不同。宿主跑在 Node，用 NodeNext、ES2022、无 DOM；客户端跑在浏览器，用 ESNext + Bundler、DOM、react-jsx。客户端 tsc 只出声明，JS 交给 esbuild 打成单个 classic script。混用会让 DOM 类型漏进宿主，或让客户端拿到 Node 类型。
Q3. files 里漏了 cordis.patch.yml 会怎样？
参考答案
npm 包不带这个文件，dsh.bundle.patch 指向的文件不存在；dsh plugin add 会把包当普通依赖安装并警告，插件不会被自动接线。安装后 --dump-config 里看不到条目。
Q4. dsh plugin add 遇到不兼容的 peer 会警告后继续吗？
参考答案
不会。peer 是强制检查，安装直接失败，并打印 allow-version ... --accept-risk 豁免命令。只有明确知道风险时才用豁免。

本节最佳实践

  • 构建链 fail fast：产物断言放最后，缺文件直接非零退出；不要用 || true 吞掉。
  • files 用白名单，只发运行所需；exports 同时给 types 和 default，客户端子路径单独列。
  • 版本兼容只看 engines.dsh（存在时）和 @deepseek-ai/dsh* peer；prerelease 纳入比较；不要用 devDependencies 判断。
  • 类型检查和构建分开跑：npm run typecheck 不产 JS，npm run build 产 JS；CI 两个都跑。
  • 安装验证用全新 profile：先 --dump-config 确认配置层，再 boot 确认模块加载；本地路径安装不联网，适合反复试。
  • 客户端 bundle 的 id 必须等于包名，外部依赖只能来自 shell seed 表；构建脚本已经断言，别用 --external:* 绕过。
