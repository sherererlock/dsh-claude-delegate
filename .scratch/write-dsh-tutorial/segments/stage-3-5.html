关键代码

defineTool 收四段：身份（name + description）、parameters、output（schema + render）、execute。外加一个可选的 timeoutMs。运行时先按 parameters 解析并校验模型传来的 arguments，失败就返回工具错误，不会进 execute；execute 的返回值再按 output.schema 校验，然后交给 output.render。模型看到的是 render 返回的 content blocks，不是 execute 的原始对象。

cookbook/adding-a-tool（官方最小形态）
1import { readFile } from 'node:fs/promises'
2import type { Context } from '@deepseek-ai/cordis'
3import { defineTool } from '@deepseek-ai/dsh-tools'
4 
5export const name = 'my-tool'
6export const inject = ['tools']
7 
8export function apply(ctx: Context) {
9  ctx.tools.register(defineTool({
10    name: 'read_file',
11    description: 'Read a file from disk.',          // what the model sees
12    parameters: {
13      path: { type: 'string', required: true, description: 'Absolute path' },
14      limit: { type: 'number' },                     // optional by default
15    },
16    output: {
17      schema: { type: 'string' },
18      render: (_args, value) => [{ type: 'text', text: value }],
19    },
20    async execute(args, exec) {
21      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
22    },
23  }))
24}

parameters 是一个隐式的属性表：每个属性写 required: true 就是必填，不写就是可选。显式对象节点要声明 additionalProperties: true | false。schema 能表达的约束（类型、必填、枚举、联合、嵌套）会先校验；schema 表达不了的（非空字符串、正数、跨字段关系）仍要在 execute 里检查，并用 ToolArgsError 拒绝。

output.render 只负责模型可见的内容；UI 卡片是另一条路径，用 presentCall / presentResult 声明。本项目的 presentCall（src/index.ts:1474-1479）返回一个 generic 卡片，和 output.render 互不影响。timeoutMs 必须是正的有限值；配置里写 0 会让工具注册失败。

自测

Q1. defineTool 的四段分别是什么？哪一段写业务逻辑？
参考答案
身份（name + description）、parameters、output（schema + render）、execute。只有 execute 写业务逻辑；output.render 只是把校验后的规范值格式化成模型可见内容。timeoutMs 是附加的调度元数据。
Q2. 参数校验发生在 execute 之前还是之后？校验失败时 execute 会跑吗？
参考答案
之前。注册表按 parameters 校验模型传来的 arguments，失败就走工具错误路径，execute 不会执行。所以 execute 里不用再写一遍类型和必填检查。
Q3. execute 返回的对象和 output.render 返回的 content blocks，哪个是模型看到的？
参考答案
render 的返回值。execute 的返回值先按 output.schema 校验，再交给 render；模型上下文里只有 render 产出的 content blocks。execute 的返回值是给程序化调用方和 render 用的规范值。
Q4. presentCall 和 output.render 有什么区别？
参考答案
output.render 决定模型可见内容；presentCall 决定 UI 的 pending 卡片（标题、图标、原始参数）。两者互不影响，UI 展示失败也不该让工具结果失败。
Q5. timeoutMs 写 0 会发生什么？
参考答案
注册表要求 timeoutMs 是正的有限值，0 可能让工具注册失败。配置里要给正数；长任务按需放大，不要用 0 表示「不超时」。

官方推荐 vs 本项目做法

官方推荐：parameters 用属性表写清楚类型与必填，让 defineTool 在 execute 前完成校验并推断 args；output.schema 声明规范返回值，output.render 只负责模型可见内容；timeoutMs 是正有限值。出处：cookbook/adding-a-tool、subsystems/tools。

本项目做法：parameters 用的是正确的属性表（src/index.ts:1206-1287），但 execute(args: any, exec)（:1329）和 render(_args: any, value: any)（:1308）显式写了 any；output.schema 有 additionalProperties: false 和 properties，但没有 required（:1288-1307）；Config.timeoutMs 只有 z.number()，没有下限（:110）。

差异：schema 还在，类型契约没了。execute 里 args 可以是任何东西，render 里 value 也是；输出少一个字段照样能渲染。调用方传错参数时，错误信息来自运行时而不是类型检查。

原因：这个工具有二十多个可选参数，显式 any 是让 1481 行文件先通过 typecheck 的最快改法；输出 schema 是照着旧 JSON Schema 写的，required 当时没补。fork 自上游，历史写法一直沿用。

你该怎么做：新工具照 cookbook 写，别写 any。改这个工具时先删 any，让类型错误把要收窄的地方列出来；给输出补上你承诺的 required；给 timeoutMs 加 .min(1)。读本项目时把这几处当历史写法，不要当模板。

官方推荐：配置里有限的取值集合用 z.union([...]) 或等价枚举，非法值在加载时失败。出处：cordis-tutorial/05-config、config-catalog。

本项目做法：permissionMode: z.string()（src/index.ts:106）和 effort: z.string()（:116）都没有枚举；只有 bypassPermissions 在运行时检查配套的 allowDangerouslySkipPermissions（:342-346）。同一文件里的 thinkingMode 却用了 z.union([...THINKING_MODES])（:118），工具参数层的 permissionMode 也用了 enum（:1214-1218）。

差异：patch 里把 acceptEdits 拼错，配置能加载，错误值一路传到 SDK；工具参数层反而比配置层严。

原因：permissionMode 和 effort 的合法集合来自 Claude Code CLI，随上游版本变化；作者选择透传，避免本地枚举把新值卡住。

你该怎么做：自己插件的配置用 z.union 锁死已知集合。如果确实要跟随上游，至少在 apply 开头校验一次并给出可读错误，不要让它跑到 SDK 才失败。

本节「不要照抄」

  • 不要照抄 execute(args: any) 和 render(_args: any, value: any)。schema 在，类型却丢了，复制时很容易一起带过去。
  • 不要照抄没有 required 的 output.schema。你承诺返回哪个字段，就让 schema 也这么承诺。
  • 不要把 permissionMode / effort 写成无约束的 z.string()。
  • 不要用 timeoutMs: 0 表示不超时；注册表要求正数。
  • 不要把二十多个参数全塞进一个工具。先问每个参数是不是每次调用都需要；不需要的放到配置里。

Q1. 一次委派从工具调用到面板，经过哪些模块？
参考答案
execute → sessions.plan → 前台 / jobs.start → runWithSession → runClaude → query（SDK）→ onDelta / onEvent → JobTracker 的文本环 / 事件环 → ClaudeCodeRemote 的 @Remote → client/api.ts → ClaudeCodeView / EventView / OutputView。
Q2. 注册表级 stateOf 为什么被弃用？替代入口是什么？
参考答案
它在没有插件注册该 key 时返回 undefined，分不清「没注册」和「没有值」；官方把读取交给投影的所属服务。普通读取用 agent.model.current()，所有者内部用 awaited handle.stateOf(session)。
Q3. ctx.jobs.read 和 ctx.jobs.readAt 有什么区别？面板该用哪个？
参考答案
read 是模型消费式读取，会推进模型游标；readAt 从绝对偏移读，不动模型游标，任意多个观察者可以各读各的。面板应该用 readAt，或者像本项目一样用等价的绝对偏移环。
Q4. 本项目为什么不用 ctx.jobs.kill？这个理由现在还成立吗？
参考答案
tracker.ts:1-12 说 kill 会把作业标记为已上报，模型收不到完成通知。当前官方文档相反：packages/api/job-controller 的 kill 明确写「owner agent still receives the completion notice」。这个理由已经过期。现行代码保留自建取消路径，主要是历史实现和面板自己的取消文案；照官方做时，用 ctx.jobs.kill(id, caller, reason)。
Q5. @Remote 的方法参数名为什么不能随便改？
参考答案
SRC 模式从方法参数名生成 wire 字段。改参数名等于改协议，旧客户端会传错字段或读空。要么把参数名当公开契约冻结，要么改用生成的 Typert 契约。

官方推荐 vs 本项目做法

官方推荐：不要用注册表级 sessionProjections.stateOf(session, key)。普通读取用 agent.model.current()，所有者内部用 awaited handle.stateOf(session)；投影的读取归所属服务。出处：upgrade-guide/v0.2.1-rc.2、upgrade-guide/v0.2.1-alpha.4。

本项目做法：currentMainSelection（src/index.ts:194-215）用 ctx.get('sessionProjections') 拿到投影服务，再调 projections.stateOf(a.session, 'modelSelection')，取 pending ?? lastUsed；拿不到就退回 agent.options.model。

差异：项目用的是已弃用的同步投影读取。它依赖服务注册时机，拿不到时只能退到创建时的模型值，运行中切换的 effort 也会丢。

原因：代码来自 0.2 早期，当时这是公开入口；ctx.get 懒读取是为了绕开 cordis 4.x 没有 optional-inject 的问题（写进 inject 会阻塞 fiber），同步调用又不用改调用点为 async。

你该怎么做：新插件直接 exec.agent.model.current()。改本项目时先确认 agent 对象形状，再替换并跑一次真实委派；不要把 ctx.get('sessionProjections') 当通用模式复制。

官方推荐：后台作业通过 ctx.jobs.start({ kind, label, owner, run }) 生产；模型用消费式 read，观察者用非消费的 readAt；取消用 kill(id, caller, reason)，reason 会并入终态 detail；浏览器通过 job.list / job.follow Remote 流拿名册和输出。出处：subsystems/jobs、cookbook/adding-a-tool。

本项目做法：jobs.start 只负责登记作业和给模型 handle.append 推送（src/index.ts:989-1010）；另建 JobTracker，维护 500 KB 文本环和 2 MB 结构化事件环；remote.ts 暴露 claudeCode/readOutput、readEvents、cancel；取消走自己的 AbortController，让作业正常 settle 成 killed。

差异：官方的 readAt 已经支持绝对偏移和多观察者，文本环这一层是重复实现。官方环只保留文本 chunk（stdout / stderr / log），没有面板需要的 tool_use / tool_result / thinking 结构化事件；本项目的第二个环是为这个补的。项目注释里「kill 吞通知」的理由与当前文档相反：job-controller 的 kill 明确说 owner agent 仍会收到完成通知。

原因：fork 时的 jobs seam 还没有 readAt 和 job-controller 流；面板要的不只是文本，还有能直接渲染的块结构；官方结算后的保留量（默认 16 KB）比面板想回放的少。第一条是历史，后两条是产品需求。

你该怎么做：文本和名册优先用 ctx.jobs.readAt / job.list / job.follow；取消用 ctx.jobs.kill(id, caller, reason)。只有官方环不携带的数据（结构化事件、自己的工作流登记）才自建缓冲。不要复制 tracker.ts 头部那段已经过期的 kill 理由。

本项目做法：ClaudeCodeRemote 走 SRC 运行时反射，不做 Typert codegen（src/remote.ts:1-14）；客户端 api.ts 直接 connection.rpc.call('/api', 'claudeCode/<method>', { args })（:162-173），并在 toEvent 里逐字段重新校验（:49-110）。

原因：SRC 模式不需要 codegen，构建链更短，fork 时项目已经这么写；插件还有官方 jobs 不覆盖的数据（结构化事件、工作流登记），需要自己的 RPC。代价是两端靠人同步字段。

原因：委派目标就是 Claude Code，子代理配置要透传给 SDK；作者沿用了 SDK 的字段名，没有在插件层改名。

你该怎么做：看到 subagents 先看上下文。写 DSH 插件时，DSH 的子代理用 ctx.subagents；这个字段只在「透传给 Claude Code」时使用。文档里把两者分开写。

自测

Q1. 面板的三路 job 源分别是什么？为什么要合并？
参考答案
0.2 的 ctx.jobs 名册（jobs.state）、0.1.x 的 useSessions 镜像（jobsBySession）、插件自己的 listJobs 轮询结果（tracked）。合并是为了同时兼容 0.1.x 和 0.2，并且自己的 tracker 不会漏掉刚启动的作业。
Q2. 1 秒轮询什么时候开？什么时候关？
参考答案
只在面板挂载、选中会话还有 running 作业时开；作业进入终态后触发一次最终读取，然后不再开定时器。effect 的 cleanup 会 abort 读取并 clearInterval。ClaudeCodeView.tsx:381-441。
Q3. 当前 installStyles() 的问题是什么？怎么修？
参考答案
它只注入 <style>，没有 remove；卸载或 HMR 后标签留在 <head>，HMR 时旧内容也不会更新。加 removeStyles()，用 ctx.effect(() => { installStyles(); return removeStyles }) 注册清理。
Q4. 为什么 slots.register 要包在 slots.inject 里？
参考答案
bundle 可能早于 ui-conversation 声明 conversation.view 加载，裸 register 会抛错。inject 等 owner 声明后运行回调，owner 折叠时注册随 effect 移除，重新挂载时再运行。
Q5. 面板状态为什么放在模块级缓存，而不是组件 state？
参考答案
harness 会卸载非活动视图，组件 state 在切 tab 时丢失；模块级 panelOf(sessionId) 保留选中任务、已读偏移和输出缓存，切回来能接着读。这是本项目的视图生命周期约束，不是通用模式。

官方推荐 vs 本项目做法

官方推荐：Cordis 未管理的资源（定时器、连接、watcher、DOM 副作用）包在 ctx.effect() 里，并返回 disposer；卸载和 HMR 时都会执行。出处：cordis-tutorial/02-lifecycle-and-effects。

本项目做法：client/index.ts:26 直接调 installStyles()；styles.ts:882-891 只检查 #STYLE_ID 是否已存在，然后 append，没有 remove 函数。

差异：卸载后 <style> 留在 <head>；HMR 时靠 id 去重，旧标签挡住新内容，样式更新不会生效。

原因：一次性注入实现最简单；开发时全页刷新居多，HMR 的样式残留不容易暴露。

你该怎么做：照练习 5.2 加 removeStyles()，用 ctx.effect 返回 cleanup。不要复制「只 install 不 cleanup」的写法；在卸载时释放自己申请的资源。

官方推荐：客户端的作业数据走生成的 Remote 流（job.list / job.follow）和 client model：model 维护稳定快照，UI 订阅，不在组件里复制 transport state，也不轮询。出处：subsystems/jobs、subsystems/web-client。

本项目做法：ClaudeCodeView 合并三路源：jobs.state、useSessions.jobsBySession、自己的 listJobs 轮询（2 秒）；选中任务 live 时再 1 秒轮询 readEvents / readOutput（:231-242, :279, :381-441）。

差异：官方一套推送源加一个 client model；本项目三套源去重，加两档轮询，transport state 直接进组件。兼容路径多了，代码也就多了。

原因：要同时兼容 0.1.x（镜像）和 0.2（jobs 服务）；自己的 tracker 是唯一不会漏掉刚启动作业的源；官方 job 流没有结构化事件，live 文本也没有对应的 Client→Host 推送，只能轮询。harness 卸载视图又逼着把状态搬到模块级缓存。

你该怎么做：只面向一个 DSH 版本时，用生成的 jobs client model 和 job.follow，不要抄三路合并。必须轮询时，照这里的生命周期：只在挂载且任务运行时开表，cleanup 清掉，状态不要只放组件 state，卸载时会丢。先确认官方有没有推送，再决定轮询。

官方推荐：package.json 的 dsh.client.inject 列出客户端 bundle 依赖的包行，清单应与实际运行时一致。出处：subsystems/client-modules 的 WebBootEntry.inject。

本项目做法：package.json 里仍列 @deepseek-ai/dsh-client-runtime；0.2.2-rc.5 已经没有这个包（09 票灰色地带）。硬依赖在 src/client/index.ts:19 的 inject = ['slots', 'connection']。

差异：清单里有一个不存在的包。它当前不影响加载（09 票判断为信息性字段），但会让读者以为要装它，也会让版本升级时误判依赖。

原因：从 0.1.x fork 时留下；0.2 拆包 / 改名后没同步。代码能跑，清单就一直没改。

你该怎么做：以 inject 和实际 import 为准。自己插件只声明用到的包，发布前对照目标 DSH 版本的文件清单；不要照抄这串旧包名。

本节「不要照抄」

  • 不要照抄 installStyles() 这种无 cleanup 的一次性副作用。
  • 不要在没有 0.1.x 兼容需求时合并三路 job 源。
  • 不要在官方有推送 / 流的地方自己开 1 秒轮询。先查 job.follow。
